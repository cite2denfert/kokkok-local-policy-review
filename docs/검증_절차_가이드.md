# 근거 파일 검증 절차 (real-003 / demo-2.1-003)

검증은 두 갈래다. 데이터 담당은 근거 파일이 원본과 맞는지 확인하고, 개발자는 화면이 근거 파일대로 동작하는지 확인한다. 두 검증이 모두 통과해야 근거 파일이 확정된다. 순서는 데이터 담당 검증(A), 개발 검증(B), 결과 회신(C)이다.

## A. 데이터 담당 검증 (원본과 근거 파일이 맞는가)

| 단계 | 할 일 | 합격 기준 |
| --- | --- | --- |
| A1 | 파일 버전 확인. 실제 파일의 `dataset_version`이 `real-003`, 합성 파일이 `demo-2.1-003`인지 본다 | 두 값이 일치하고, 개발자에게 넘긴 파일과 같다 |
| A2 | `python src/10_verify_evidence.py`를 실행한다(BC 원본이 있는 비공개 환경에서) | 마지막 줄이 "전체 결과: 통과", FAIL 0개(PASS 35개) |
| A3 | 손으로 3곳 대조. 원본 CSV에서 시군구 하나를 골라 월별 전체 결제금액(T), 외국인 결제금액(성별 코드 3, F), 성별 미상 결제금액(코드 x, U)을 피벗으로 합산해 JSON의 `months[]`와 비교한다. 규모가 큰 곳, 작은 곳, 미상 비중이 큰 곳으로 3곳을 고른다 | 3곳 모두 월별 F·T·U가 원 단위까지 같다 |
| A4 | 외부 자료 대조. `ext_population.csv`의 인구 합계가 행정안전부 원본(2026-08-31 합계 51,084,159명)과 같은지, `ext_registered_foreign.csv`의 시군구가 255개인지 본다 | 합계 일치, 255개 전부 매칭. 화성시 4개 구 1월만 등록외국인이 비어 있다 |
| A5 | 임계값 재점검(선택). `python src/11_threshold_decision.py`를 실행해 `임계값_결정표.md`의 숫자가 재현되는지 본다 | 결정표의 재현성·발동 비율이 같다 |
| A6 | 결과를 비공개 검증 기록에 남기고, 개발자에게는 시군구별 값이 없는 공개용 요약만 준다 | 두 파일 모두 같은 날짜와 파일 버전이 적혀 있다 |

### A2 자동 검증 35항목 (`src/10_verify_evidence.py`)

| 구분 | 항목 | 내용 |
| --- | --- | --- |
| S 구조 | S01~S07 | 실제·합성 파일 버전, 기록 수(255+전국, 12+전국), 최상위·월별·하위 블록 키 구성이 같은지, R08 참고 표시, 임계값이 설정 파일과 같은지 |
| M 합계 | M01~M07 | 업종·연령·외국인 업종 비중 합 100, 월별 T·C 합 = 6개월 합, 전국 기록 = 시군구 합, F≤T·U≤T·비중 0~100 |
| R 원본 재계산 | R01~R04 | 원본 행 수·시군구·월·업종, 표본 14곳의 월별 F·T·U·C와 업종 비중, 전국 월별 합. 근거 파일 생성기(pandas 피벗)와 다른 방식(csv 행 단위 누적)으로 계산 |
| A 집계값 | A01~A08 | 결제 없음 57건, R03 유형 분포(39·39·50), 소액 지역 51곳, R04 발동 30곳, R12 대상 51곳이 원본 재계산값·보고값과 같은지, R04 기준·발동월·R02 컷오프의 내부 일관성 |
| D 합성 | D01~D09 | 합성 파일에 실제 시군구 이름이 없는지, 합성 시나리오 A~L이 기대대로 켜지는지 |

`--mode check`는 보고값(57건·30곳 등) 대신 원본 재계산값과만 비교한다. 가짜 원본으로 실행 점검할 때 쓴다.

FAIL이 나오면 그 항목의 원인을 먼저 찾는다. 원본이 바뀌었는지, 임계값이 바뀌었는지, 스크립트를 고쳤는지를 본다. 원인을 모른 채 검증 값을 고쳐 통과시키지 않는다.

## B. 개발 검증 (화면이 근거 파일대로 동작하는가)

| 단계 | 할 일 | 합격 기준 |

| B1 | 합성 파일(`examples/review_evidence_demo_v2.1.json`)로 스키마 검증 테스트를 만든다. 필수 키와 자료형을 확인하고, 모르는 키가 있어도 오류 없이 동작하는지 본다 | 테스트 통과 |
| B2 | 합성 시군구 A~L 시나리오 12개를 화면에서 재현한다(`근거파일_스키마_2.1.md` 6장 표) | 12개 모두 표의 기대 동작과 같다 |
| B3 | 2.1 변경점 반영 확인. `region_basis`가 `merchant_location_assumed`일 때 R02가 막히지 않는지, `applicability`의 R08·R09·R11·R12를 읽는지, `months[]`의 `season_index`·`season_flag`를 쓰는지 본다 | 3가지 모두 확인 |
| B4 | R04는 화면에서 다시 계산하지 않고 `season_summary.threshold`와 `season_flag`를 그대로 쓰는지 확인한다 | 화면 표시가 JSON과 같다 |
| B4a | R08이 확정 판정이 아니라 참고용으로 표시되는지 확인한다(`applicability.R08.display_level`) | 화면에 "참고" 표시가 있다 |
| B5 | 실제 파일로 시군구 3곳 이상을 골라 화면 값과 JSON 값을 대조한다(규모 차이가 큰 두 곳, 미상 비중이 큰 한 곳) | 표시 값이 JSON과 같다 |
| B6 | 예외 동작. `external`이 `null`일 때(합성 L), 결제 없음 업종, 3월 `no_data`(합성 B), 외국인 결제 규모 부족으로 R03 유형이 표시되지 않을 때(합성 I) | 화면이 깨지지 않고 문구가 나온다 |
| B7 | 보안. 저장소 변경분에 실제 파일이 없는지, `private/`가 `.gitignore`에 있는지, 배포 결과물에 실제 JSON이 없는지 본다 | 실제 파일이 어디에도 없다 |

## C. 검증이 끝난 뒤 (결과 주고받기)

| 방향 | 무엇을 | 어떻게 |
| --- | --- | --- |
| 데이터 담당 → 개발자 | 검증 결과 요약(통과 항목과 집계 숫자, 시군구별 값 없음) | 공개용 묶음에 함께 넣는다. 파일 버전과 검증 날짜를 적는다 |
| 개발자 → 데이터 담당 | B1~B7 결과 | 합격이면 그대로 회신하고, 불일치가 있으면 시군구와 필드 이름, 화면 값, JSON 값을 적는다 |
| 데이터 담당 → 개발자 (불일치 시) | 고친 근거 파일 | 원인을 찾아 근거 파일을 다시 만들고 `dataset_version`을 올린 뒤 A를 다시 하고 새 요약을 넘긴다 |

- 실제 근거 파일이 들어 있는 검증 기록은 개발자에게 넘기지 않는다. 표본 시군구 이름과 원본에서 나온 값이 들어 있다.
- 두 검증이 모두 통과하면 파일 버전을 확정 버전으로 기록하고, 이후 임계값이나 원본이 바뀔 때만 다시 만든다.
- 사용자 검증(담당자 몇 명에게 화면을 보여 주고 질문 개수와 문구를 확인)은 이 검증과 별개이며, 여기서 임계값 조정이 나올 수 있다.
